## Finding 1: A row left `running` locks the run for good after any job failure
- **Severity:** Critical
- **Location:** Phase 2, sections "Row states" and "Commands"; Phase 4, sections "Kinds" and "Parked row questions" ("Queue again")
- **Flaw:** `webtest-next` writes `running` to `run.json`, which lives as long as the run. The only thing that clears it is the orchestrator, which lives only as long as the job. The state table allows `running` to move only to `pass`, `fail` or `parked`, and refuses every other transition. No command resets a `running` row. Three commands refuse any run that still has one: `webtest-run` (phase 4 line 31), `webtest-close` (phase 2 line 92) and `webtest-export` (phase 3 line 56).
- **Failure scenario:** Row r17 is `running`. The job then fails for one of these reasons: the server restarts (`server-stopped`), the session goes quiet for 15 minutes and another session takes over (`session-lost`), or the agent runs `console wait` again (`not-closed`). The tester presses "Queue again". `webtest-run` refuses because the run has a `running` row. `webtest-close` and `webtest-export` refuse for the same reason. The run can never be finished, so acceptance criteria 3 and 9 are unreachable unless someone edits `run.json` by hand. Phase 2 line 129 then rejects a hand-edited file that does not validate.
- **Evidence:** `scripts/testign/console/jobs.py:460-470` (startup fails every active job as `server-stopped`); `jobs.py:698-707` (another session takes over after `SILENT_WITH_JOB` and fails the job as `session-lost`); `jobs.py:774-778` (`wait` fails the open job as `not-closed`); `jobs.py:48` (`SILENT_WITH_JOB = 15 * 60.0`). Plan phase 2 line 78: "Any other transition is refused."; line 88: `webtest-next` "Refuses: A run that already has a `running` row"; phase 4 line 63: "'Queue again' starts a new `webtest-run` job on the same run, which continues from `run.json`".
- **Suggested fix:** Record the owning job id on the `running` row. Add one allowed transition, `running → queued` (or `not-run: interrupted`), that `webtest-run` applies at start when the owning job is finished. Add a test: fail the job in the middle of a row, queue again, and check that the row runs.

## Finding 2: Parked questions and self-run results are kept by the job, but the parked row belongs to the run
- **Severity:** Critical
- **Location:** Phase 4, section "Parked row questions (non-blocking)"; Phase 6, section "Skill: run job"
- **Flaw:** The question, the tester's answer and the self-run result live in the job record as `parks`, which lasts as long as the job. The row's `parked` state lives in `run.json`, which lasts as long as the run. Nothing carries open parks over to a new job. The self-run image sits in the upload folder, which is swept after one hour.
- **Failure scenario:** Eight rows are parked and the server restarts. The old job becomes `failed`, and its parks cannot be answered, because answers are only taken while a job is open. "Queue again" creates a new job with zero parks. The run loop sees an empty queue with `open: 0`, never waits, runs `webtest-close`, and all eight rows become `not-run: unanswered`. The tester was never asked. Separately, a tester who uploaded a self-run screenshot before the failure loses it to the one-hour sweep. After 7 days or 50 finished jobs the pruner also deletes the only copy of the question text. Acceptance criteria 3 and 5 are broken: criterion 3 sees a reason that is false, and criterion 5 sees a question that disappeared.
- **Evidence:** `scripts/testign/console/jobs.py:51-52` and `474-485` (`PRUNE_AGE`, `KEEP_FINISHED`, pruning deletes the record); `jobs.py:656-672` (answers need an open job); `scripts/testign/console/templates_api.py:29-30` and `87-103` (`UPLOAD_TTL = 3600`, the sweeper deletes the folder). Plan phase 4 line 50: "Stored in the job record as `parks`, keyed by row"; line 63: "A failed or cancelled job leaves its parks in the record"; phase 6 lines 74-75 (close when no park is open).
- **Suggested fix:** Store the park question, answer and self-run result in `run.json`. The orchestrator writes them through `webtest-park`, and the server writes only to a separate answers file under `~/.testign-kit/webtest/answers/<run>.json`. The job then shows a view of the run's open parks. Copy self-run images when they arrive, not when the agent next polls.

## Finding 3: Evidence capture has no working route unless the debug connection works, and the main evidence command belongs to no phase
- **Severity:** Critical
- **Location:** Phase 1, section "Spike items" B and D; plan.md, section "Load-bearing assumptions" row 2; Phase 2, section "Run folder"; Phase 6, section "Skill: run job" step 3
- **Flaw:**
  1. B1 assumes "a file path from the Chrome tools". Claude in Chrome screenshots return an image to the model, not a file. The research report names no file-producing tool (research Q1 has no such row). In practice B depends on B2.
  2. B2 is the debug port of "a dedicated profile". That profile only shows what Claude sees when D2 passes, meaning the Claude extension works inside it. The research marks D2 as likely broken on macOS (native-messaging file, research line 68). With D1 (approval mode), each new connection opens a Chrome dialog (research line 48). A per-row CLI process that captures evidence therefore raises 45 dialogs during an unattended queue.
  3. No route says which of Claude's tabs to capture or which area to clip. In headed Chrome, `Page.captureScreenshot` on a background tab is unreliable.
  4. Phase 6 calls `webtest-evidence` for agent rows. Phase 2's command table does not include it, and phase 4 adds only `--from-upload`. No phase owns the capture command or its interface.
  5. The plan stops and replans when B fails, yet the tester-upload route it builds in phase 4 could meet acceptance criterion 4 for the same rows.
- **Failure scenario:** Possibility A: B1 fails, D1 passes and D2 fails on macOS, which matches the research's prediction. Every row then blocks on a Chrome approval dialog nobody is watching, and the run stalls. Possibility B: D fails entirely. The plan then says "stop and replan" after phases 2-4 (8 days) are already built, with `webtest-row` refusing `pass`/`fail` without a file, so every agent row is unfinishable.
- **Evidence:** Plan phase 1 line 32 ("Fallback when it fails: None ... stop and replan"); line 37 ("Item D decides item B's second route: both need a debug connection"); plan.md line 112; phase 2 line 30 ("written by the evidence command") and lines 84-93 (no `webtest-evidence` row); phase 4 line 86 (only `--from-upload`); phase 6 line 70; research lines 48 and 68. Upload route that could serve as a fallback: `scripts/testign/console/templates_api.py:128-149` (today it accepts zip workbooks only, `check_zip` at line 69).
- **Suggested fix:** Make B2 explicitly depend on D1 or D2. In D1, require one long-lived connection, held by the orchestrator, that is approved once per run. Give `webtest-evidence --tab <url-or-target> --clip` to one phase (phase 5) with tests. Name a manual evidence route as the fallback instead of "stop": the tester attaches a screenshot per row through the self-run upload. Then a failed B1 and D does not cancel the plan.

## Finding 4: "Read the ancestors of the target node" has no Figma tool, and the change table points at components rather than screens
- **Severity:** High
- **Location:** Phase 1, section "Spike items" C and section "Risks"; Phase 6, section "Skill: plan job" steps 2 and 4, and section "Triage rules" (`design-only`)
- **Flaw:**
  1. `get_metadata` returns the outline of the given node downward (its subtree). It has no ancestor or parent query. So "one call per row" (phase 1 line 84) is false. To find a parent you must pull the whole page outline and search it, which for a production file is one very large reply per page, often cut off.
  2. Ids such as `I625:18321;294:4398` belong to a layer inside an instance. The changed design lives in the main component (`294:4398`), and the screen is wherever instance `625:18321` sits. A main-component node (for example `194:5977` in the case schema) usually has no screen ancestor at all.
  3. The `design-only` rule ("a component variant with no page that uses it") requires finding every instance in the file. No tool does that.
  4. Capture images must exist as files (`webtest-import --captures <dir>`, `source/r02.png`). Figma `get_screenshot` returns an image to the model, the same file-route gap as evidence, and no spike item covers it.
  5. Budget: research line 85 counts about 3 calls per case. 45 rows plus ancestor lookups is about 180 of the 200 daily calls on Professional. Spike items C and E spend calls the same day.
- **Failure scenario:** Item C's five hand-picked rows include frame-level nodes and pass at 4 of 5. On the real table, most rows target components or instance layers. The agent marks them `confidence: low` with an empty screen, or wrongly as `design-only`, which goes to `not-applicable`. The tester fills 30 or more screens by hand, which defeats the outcome. Or the import hits the daily cap partway and acceptance criterion 1 ("45 cases") needs a second day.
- **Evidence:** Research line 87 (`get_metadata`: "lightweight XML outline of your selection ... layer IDs, names, types, positions, and sizes"); research line 85 (about 3 calls per case, 200 a day); plan phase 1 line 33 ("read the ancestors of the target node"), line 84 ("Reading Figma ancestors costs one call per row"); phase 6 lines 23, 43, 45 and 60; phase 2 lines 29, 43 and 86 (captures as files).
- **Suggested fix:** Add spike item C2: on 10 random rows, not hand-picked ones, measure how many target nodes are main components or instance layers, and how a parent is actually found (page outline size, truncation). Add item F: how a Figma capture becomes a PNG on disk. Pick item C's rows at random. Count Figma calls against the daily cap including the spike's own spend.

## Finding 5: The allowed hosts are set by commands the agent runs, so the CLI host check does not hold page text back
- **Severity:** High
- **Location:** plan.md, section "Load-bearing assumptions" row 6; Phase 2, section "Commands" (`webtest-new --host`); Phase 4, section "Kinds" and section "Review-table ask"; Phase 5, section "Commands" (`login-project-set`)
- **Flaw:** Hosts are stored in three places that never agree. The `webtest-plan` job params hold `hosts` typed by the tester. `run.json` holds hosts set by the orchestrator through `webtest-new --host <h>...`. `projects.json` holds hosts set by the orchestrator through `login-project-set --host` and by the tester in the console. Nothing ties `run.json` hosts to the job's tester-given hosts, and the review table (phase 4 lines 38-41) does not show hosts for confirmation. The plan still claims "the host check in the CLI ... keep[s] writes behind the tester either way".
- **Failure scenario:** One row's Content reads "see the new partner page at partner.example.net". The model treats it as a fact and calls `webtest-new ... --host partner.example.net`, or `login-project-set` with the extra host. That is a legitimate-looking flag, and nobody confirms it. Off-site navigation is then recorded as `pass`, and acceptance criterion 7 holds only on paper. A sign-in host the tester adds in the console reaches `projects.json` but not `run.json`. A row that lands on the SSO host after a redirect becomes `not-run: off-site` even though the tester allowed that host.
- **Evidence:** Plan.md line 116 ("the host check in the CLI and the tester-only delegation keep writes behind the tester either way"); phase 2 line 84; phase 4 line 30 (`hosts` optional list in the job params); phase 5 lines 32, 55 and 86. Existing pattern this breaks: job parameters are validated once by the server and handed to the agent read-only, `scripts/testign/console/jobs.py:580-605` and `jobs.py:905-907` (`_agent_view`).
- **Suggested fix:** Use one store for hosts. The server writes `run.json`'s `hosts` from the job params (or `webtest-new` takes `--job` and copies the params), `webtest-new` refuses `--host` values not in the job, and the review table shows the host list for confirmation. Project sign-in hosts stay separate and are used only by the runner.

## Finding 6: Whether a scenario is "signed in" is something the agent claims; it is not stored and cannot be checked, and expired logins turn sure rows into choice rows
- **Severity:** High
- **Location:** Contract, acceptance criterion 6; Phase 2, `webtest-next --signed-in`; Phase 4, section "Login prompts"; Phase 6, section "Worker brief"; Phase 1, item D
- **Flaw:**
  1. "A scenario that has not been run in this session" has no stored owner. The only record is the orchestrator passing `--signed-in <scenario>`. That value lives in the model's context, so a new job or a compacted context can claim it without a login.
  2. Chrome cookies follow their own lifetime. A site session can expire in the middle of a run, or still be valid from yesterday.
  3. The worker brief ends a row as `stuck` on a login page. A parked `sure` row is permanently moved to `choice`. Answering `delegate` requires `preconditions`.
  4. Switching scenarios on the same hosts shares one cookie jar, and the step kinds have no logout step. `goto login_url` while signed in as another account usually redirects away, so the first `fill` fails.
  5. On D2, two connected browsers (default profile and dedicated profile) need `/chrome` or `select_browser`. Nothing makes the worker use the signed-in one.
- **Failure scenario:** The site session times out after 30 minutes. Row 12 onward meets the login page. Each row parks, becomes `choice`, and needs the tester to type preconditions so it can be delegated back. 30 sure rows end as `not-run: unanswered`, or the tester types filler text. Alternatively, the run switches from `member` to `admin`. The runner's `goto /login` redirects to `/mypage`, `fill #email` fails, and the `login` ask stays open, which blocks the queue.
- **Evidence:** Plan phase 2 line 78 ("A `sure` row that parks moves to class `choice`"), line 87 (choice plus agent needs preconditions), line 88 (`--signed-in`); phase 4 line 58 (`delegate` needs `preconditions`); phase 5 line 54 (closed step kinds, no logout); phase 6 line 68 and line 85 ("A login page ... ends the row as `stuck`"); research line 21 (`select_browser`). Session identity today exists only for the agent and the browser, not for the site: `scripts/testign/console/server.py:213` (`_sessions` in memory).
- **Suggested fix:** Store `signed_in: {scenario, at, job}` in `run.json`. Only the server's login-ask resolution writes it, and it is reset when the job changes. Add a worker verdict `session-lost`, separate from `stuck`, which re-opens the `login` ask without changing the row's class. Add an optional `logout_url` step, or clear cookies for the hosts before a scenario switch. Spike D also tests switching between two scenarios.

## Finding 7: Templates with only an `item` column leak into `/testign:testcase`, and the console cannot register them
- **Severity:** High
- **Location:** Phase 3, section "Role changes (additive)"; plan.md, section "Key decisions" (last row)
- **Flaw:** The registry `~/.testign-kit/templates/index.json` is one store shared by every job kind. Phase 3 allows registering without `trace` through a new keyword argument. Neither `_check_testcase` nor `read_trace` filters by role. The console upload route still calls `register` with the default required roles, and `templates_api.py` is not in phase 3's file list. Header detection picks the header row by finding the `trace` role. A web template without 備考 falls back to "the row with the most text in the first sheet", which is the cover sheet in the plugin's own sample layout. The shipped sample has a dropdown `OK,NG,保留,対象外` on 結果, while the default `verdict_labels` are `Pass` / `Fail`.
- **Failure scenario:**
  1. Through the console, a tester uploads a web template without 備考 and gets `mapping-failed (missing: trace)`. The "New run" form requires a template from that list.
  2. If the CLI registers it with item only, the tester then queues `testcase` in `trace` mode with that template. `read_trace` raises `KeyError: 'trace'` and the job crashes. That breaks the constraint that existing behaviour stays the same.
  3. A sample-based workbook gets `Pass` in a column that only allows OK/NG.
- **Evidence:** `scripts/testign/templates.py:21` (`REQUIRED_ROLES = ["item", "trace"]`), `templates.py:140-141` (header row picked only when `"trace" in roles`), `templates.py:142-156` (fallback to the first sheet), `templates.py:253` (missing-role check); `scripts/testign/console/templates_api.py:188-192` (console register uses the defaults); `scripts/testign/xlsx.py:168` (`cols["trace"]`, no guard); `scripts/testign/console/jobs.py:351-357` (testcase lists every template); `xlsx.py:192-205` (cover sheet first) and `xlsx.py:214` and `227-229` (結果 dropdown OK/NG). Plan phase 3 lines 48 and 102.
- **Suggested fix:** Record `purpose` (or the required roles) on each registry entry. `_check_testcase` refuses entries without `trace`. Add the required-roles option to the console register route and UI. Detect the header row by any two mapped roles instead of `trace`. Default `verdict_labels` from the dropdown values of the result column when one exists.

## Finding 8: A 45-row run in one conversation outlasts the job's silence limit and the model's context, and permission prompts go where the tester is not looking
- **Severity:** High
- **Location:** Phase 6, sections "Skill: run job" and "Worker brief" (fallback paragraph); Phase 1, item E; plan.md assumption row 1
- **Flaw:**
  1. The orchestrator talks to the server only between rows. If a row takes 15 minutes or more, the job is marked silent, the tester may mark it failed, and another session can take over. Either way the job fails, and Finding 1 applies.
  2. On the fallback route (spike A fails), the orchestrator runs all 45 rows in its own context with page reads and screenshots. "Clears what it read of the page ... as far as the runtime allows" is not a capability Claude Code has. The context compacts in the middle of the run. The console skill requires the agent to keep `session` and the job id for the rest of the conversation.
  3. Claude in Chrome permission prompts ("Claude in Chrome wants to"), including prompts raised by subagents, appear in the terminal session. The plan sends the tester to the console and never shows them there.
  4. Spike item E times only five rows, so it cannot reveal any of this.
- **Failure scenario:** On row 9 the worker opens a new subdomain and a site-permission prompt appears in the terminal. The tester is watching the console, which shows "running". After 15 minutes the job turns silent. The tester presses "Mark failed", or a second Claude session attaches. The job fails and the run is stuck (Finding 1). On the fallback route, compaction near row 25 drops the console `session` id. The next `console progress` returns `session-replaced`, and the skill says "Never retry the same failing call in a loop."
- **Evidence:** `scripts/testign/console/jobs.py:48` (`SILENT_WITH_JOB = 15 * 60.0`), `jobs.py:628-635` (`mark_failed`), `jobs.py:690-707` (takeover after silence); `skills/console/SKILL.md:32-33` ("Keep that `session` id for every later `console` command in this conversation"), `skills/console/SKILL.md:103`; research line 18 (prompts from a background subagent show in the main session). Plan phase 6 lines 88-89; phase 1 line 35.
- **Suggested fix:** Have the orchestrator send `console progress` as a heartbeat while a worker runs (or hold `parks --wait` with a short timeout as a keep-alive). Make item E run 15 consecutive rows on both routes and record context use. Add a console banner "the agent may be waiting for a browser permission in the terminal" when no progress arrives for N minutes. Write the session id and job id into `run.json` so the run can recover after compaction.

- **Location:** plan.md frontmatter `effort: 20d`; Phase 5, sections "Context", "Tasks & Steps" and "Verification"; Phase 7, sections "Context" and "Verification"
- **Flaw:**
  1. The phase efforts add up to 2 + 2.5 + 2.5 + 3 + 3 + 3 + 4 + 2 = 22 days, not 20, before counting the Windows spike and the rounds that run through the user's machine.
  2.   4. Phase 7 names the i18n parity test as `ui/tests/i18n.test.mjs` and runs it with `node --test`. The parity check (same keys, no empty values) is actually the Python test.
