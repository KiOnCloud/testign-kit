# Red team: Scope & Complexity Critic (Contract Verifier)

Plan: `plans/261119-0324-web-ui-test-runs-from-figma/` (plan.md, phases 1 to 8). Reviewed 2026-11-19.
Requested scope (one command and console UI, Figma source, brainstorm/confirmation with column
mapping and samples, sure/choice triage with tester choice, orchestrator and worker with parking,
queue only, login scenarios per project with a menu and agent-offered creation, declarative step
list with a fixed runner, credentials in a console form, Excel plus Markdown, always through the
console) is treated as fixed. The findings below cover additions, duplicated mechanisms and
interface changes whose consumers the plan does not list.

## Finding 1: Parked questions add a second question channel where the existing `ask` already polls without blocking
- **Severity:** High
- **Location:** plan.md, "Key decisions", row "Parked row questions are a second, non-blocking question channel"; Phase 4, section "Parked row questions (non-blocking)"
- **Flaw:** The plan justifies a new channel with "`Bridge.ask` holds the call until the answer arrives (`console/jobs.py:849-866`), which would stop the queue". The hold length is set by the caller. `timeout: 0` is accepted and returns `{answers: null}` at once. Asking again with the same id returns the stored answer, so redelivery is already safe to repeat. The real limit is one open ask per job. The plan does not lift that limit. It builds a parallel store instead: `parks` in the job record, three agent routes, three client commands, a `parks-ack` acknowledge protocol, a browser answer route, a `finish` route, a second `done` guard and its own session-age check.
- **Failure scenario:** (a) Parks keep the job `running`, so `state_view.needs_input` stays 0 and the sidebar's "needs you" badge never lights for a parked row. The tester does not know a row is waiting, and the run sits in `console parks --wait` until the 540 s cap, again and again. (b) The ack protocol does again what `asked` already does by id. A crash between `webtest-resolve` and `parks-ack` hands the same answer out twice; `webtest-resolve` then refuses it ("does not fit the row's state") and the skill has to tell that refusal apart from a real error. (c) Two answer paths must keep the anti-self-approval rule (`jobs.py:662-668`) in step forever.
- **Evidence:** `scripts/testign/console/jobs.py:913` (`value < 0` refused, 0 allowed); `jobs.py:864-868` (deadline passes, returns `{"answers": None}`); `jobs.py:838-842` (answered ask id is handed out again); `jobs.py:844-845` (the real limit: "another question is still open on this job"); `jobs.py:546` (`needs_input` counts only `state == "needs-input"`); `scripts/testign/console/ui/views/shell.mjs:143-147` (badge driven by `needs_input`); `references/console-bridge.md:30` ("`{answers: null}` means nothing yet: call again").
- **Suggested fix:** Extend `ask` instead. Allow several open asks per job, keyed by id. Add a `park` ask type with the fixed choice set `delegate | self-run | skip` that does not move the job to `needs-input` (or count it in `needs_input` separately). The orchestrator polls with `console ask --timeout 0`. This reuses `answer()`, the session-age check, `asked` history and redelivery by id. `done` refuses while any non-park ask is open, and "Finish" is an answer to a single `finish` ask. That removes three routes, three client commands and the ack protocol.

## Finding 2: Registry role changes are unnecessary for a run-owned column plan, and they break existing tests and the shared registry
- **Severity:** High
- **Location:** Phase 3, sections "Role changes (additive)" and "Verification"; plan.md "Key decisions", last row
- **Flaw:** The column plan already stores `template`, `sheet`, `header_row` and `field → letter`. The plan itself says free columns "are a property of one run, not of the customer's template". Writing by letter needs no registry role. Even so, Phase 3 adds `result`, `actual` and `executed_at` to `ROLES` with header synonyms, and adds a "required roles" keyword to `register()`. Registration is per template, not per run. A template registered with "item only" is then offered to `/testign:testcase`, which reads `cols["trace"]` without a guard.
- **Failure scenario:** (a) The shipped sample has 結果 in F and 実施日 in G. With the new synonyms, `detect_layout` returns two more columns. `test_shipped_sample_is_committed_and_detectable` fails on its exact dict, and the pinned `template-preview` golden output gains two role rows. Phase 3 claims "every existing template test passes without edits"; this is false on the first run. (b) A tester registers a web template without 備考 through the new keyword, then queues a trace job with it: `read_trace` raises `KeyError: 'trace'`. `_check_testcase` does not filter templates by required roles. (c) The console's template screen hard-codes the six roles and `REQUIRED = {item, trace}`. It cannot map or show the new roles and still refuses to save a template without `trace`. That screen is not in the plan.
- **Evidence:** `scripts/testign/xlsx.py:214` (sample headers include `結果`, `実施日`); `tests/test_templates_xlsx.py:57` (exact columns dict); `tests/test_templates_xlsx.py:251-253` and `tests/fixtures/template-preview-golden.md:7-14` (pinned role table); `scripts/testign/templates.py:367` (preview loops `ROLES`); `scripts/testign/xlsx.py:164-168` (`cols["trace"]`); `scripts/testign/console/jobs.py:352-360` (`_check_testcase` takes any registered template); `scripts/testign/console/ui/views/templates.mjs:11-12,305-313,355`; `scripts/testign/console/templates_api.py:162-164,188`; `scripts/testign/cli.py:129-141`.
- **Suggested fix:** Leave `ROLES`, `REQUIRED_ROLES` and `register()` untouched. Put the result/actual/executed synonyms in `webtest_export.py` for the first guess only, and read headers with `templates.headers_at(path, sheet, header_row)`. If a template without 備考 must be usable for web runs, let the column plan carry its own `sheet` and `header_row` (it already does) instead of making registry entries depend on the consumer. If the registry change is kept, list every consumer above and add a guard in `_check_testcase`.

## Finding 3: Phase 3 builds a second row writer and a second sample template next to the existing ones
- **Severity:** Medium
- **Location:** Phase 3, sections "Role changes (additive)" (web sample), "Files to Create / Modify" and "Risks" (verdict labels)
- **Flaw:** `_write_rows` already writes `columns.items()` (key → letter) with style copy and formula keep. A column plan is the same shape (field → letter). Only the source of values differs. The plan writes "a plan-based row writer beside `_write_rows`" that repeats the style-copy and formula-keep logic. It also ships `templates/webtest-template-sample.xlsx` with a `template-sample --kind webtest` flag, but the shipped sample already has `結果` and `実施日` columns and a result dropdown.
- **Failure scenario:** A style or formula fix later lands in one writer only. The two writers drift, and a customer template fills differently for testcase and webtest. The default `verdict_labels` `Pass` / `Fail` also do not match the shipped sample's own dropdown (`OK,NG,保留,対象外`). On the most likely first run (no customer template, shipped sample), every verdict cell breaks the sheet's data validation.
- **Evidence:** `scripts/testign/xlsx.py:72-98` (`_write_rows`: style copy at 79-82, formula keep at 93-94, values by key at 83-96); `scripts/testign/xlsx.py:214` (headers `結果`, `実施日`); `scripts/testign/xlsx.py:227-228` (dropdown `OK,NG,保留,対象外` on F5:F500); `scripts/testign/cli.py:659-661` (`template-sample` exists); `README.md:132` and `skills/testcase/SKILL.md:30` (the one sample is documented).
- **Suggested fix:** Give `_write_rows` a values callback (or a precomputed values dict per row) and call it from both paths. Drop the second sample and the `--kind` flag; use `testcase-template-sample.xlsx`. Default `verdict_labels` to the dropdown's values when the result column has list validation.

## Finding 4: `webtest-evidence`, the only route to acceptance 4, has no owning phase and no spec
- **Severity:** High
- **Location:** Phase 2, sections "Run folder" and "Commands"; Phase 4, "Files to Create / Modify"; Phase 5, `devtools_client.py`; Phase 6, "Skill: run job" step 3
- **Flaw:** Phase 2 says `evidence/` is "written by the evidence command", but its command table (ten commands) has no `webtest-evidence`. Phase 4 adds `--from-upload` to a command that does not exist yet. Phase 5 says `devtools_client.py` serves "the evidence command". Phase 6 calls `webtest-evidence` before every `webtest-row`. No phase defines its arguments, the naming rule (`<row>-<n>.png`), the size cap, or which route (Chrome tools file path or debug port) it implements. Phase 2 tests require `webtest-row` to refuse `pass`/`fail` without an evidence file. That makes this command a dependency of Phase 2 tests, yet it is only built in Phase 4 or 5.
- **Failure scenario:** Phase 2 lands with `webtest-row` refusing every result, because nothing can put a file into `evidence/`. Phase 6's dry run then has no command to call, and acceptance 4 (evidence on disk for every pass/fail) has no implementation owner.
- **Evidence:** Plan text: phase-02 line 30 "written by the evidence command"; phase-02 lines 82-93 (command table, no `webtest-evidence`); phase-04 line 86 "Modify: `scripts/testign/webtest.py` (`webtest-evidence --from-upload`)"; phase-05 line 96; phase-06 line 70. No such command exists in the codebase today: `scripts/testign/cli.py:540-600` (console subparsers) and `cli.py:659` (last template command).
- **Suggested fix:** Add `webtest-evidence --run --row (--from-file <png> | --from-devtools)` to the Phase 2 command table with naming, signature and size checks. Make Phase 1 item B name which flag Phase 6 uses.

## Finding 5: Self-run evidence upload is beyond every acceptance criterion and relies on an upload route that refuses images
- **Severity:** Medium
- **Location:** Phase 4, section "Parked row questions", bullet "Self-run results use the same store"; Phase 7, Run screen "enter a self-run result with an image"
- **Flaw:** Acceptance 3 needs `self-run (with the tester's result)`. Acceptance 4 needs evidence only for `pass` and `fail`. The plan still adds an image upload for self-run results, `webtest-evidence --from-upload`, and a PNG/JPEG signature check. It says the image "goes through the existing upload folder (`console/templates_api.py:37`)". That upload route accepts only `.xlsx`/`.xlsm` that pass a zip check, so a new binary image route is needed. The plan does not list one. Uploads are also deleted after one hour, while a self-run answer may wait much longer for the orchestrator to call `webtest-evidence --from-upload`.
- **Failure scenario:** The tester uploads a PNG and gets `bad-extension` / `not-a-workbook`. Or, if a new route is built, the tester attaches the image, the orchestrator is in `parks --wait` on another row, the sweep runs, and `--from-upload` finds nothing. The row then fails a check that no criterion required.
- **Evidence:** `scripts/testign/console/templates_api.py:62-63` (extension must be `.xlsx`/`.xlsm`); `templates_api.py:66-70` (`PK\x03\x04` zip check); `templates_api.py:29,98` (`UPLOAD_TTL = 3600`, sweep); `templates_api.py:270` (the only upload route is under `/api/templates/uploads`).
- **Question (requested-scope doubt, not a cut):** Does the tester want image evidence for self-run rows? If yes, list the new image upload route and copy the file into the run folder when it is received, not when the orchestrator next polls. If no, a self-run result is `verdict` plus `actual` text.

## Finding 6: The run never records its project, and hosts live in three separate lists
- **Severity:** High
- **Location:** Phase 2, "Commands" (`webtest-new`) and "Case schema"; Phase 4, "Kinds"; Phase 5, "Store" and "Commands" (`login-project-set`)
- **Flaw:** Login scenarios, credentials and the runner route are keyed by project (`login/<project>/<scenario>/`, `/api/webtest/login/:project/:scenario/...`). The `webtest-plan` job takes `project`, but `webtest-new` has no `--project`, `run.json` has no project field, and the `webtest-run` kind takes only `run` and `tester`. Hosts are kept three times: run hosts (`webtest-new --host`, job param `hosts`), project hosts (`projects.json`), and per-project sign-in hosts added in the console.
- **Failure scenario:** A run job reaches `need: "member"` and opens the `login` ask. The ask, the Sign-in button and the runner all need `:project`, and nothing in `run.json` holds it. The skill guesses, or the job fails. Separately, the tester adds `www2.example.com` to the project's hosts in the Login screen, but the run's allowed hosts came from `webtest-new`. The scenario signs in on www2 and every row that lands there is recorded `not-run: off-site`. The reverse case also happens: a run host is missing from the project, and `login-scenario-save` refuses a valid scenario.
- **Evidence:** Plan text: phase-02 line 84 (`webtest-new` arguments, no project); phase-04 lines 30-31 (`project` on `webtest-plan` only; `webtest-run` has `run`, `tester`); phase-05 lines 31-35 and 86. Codebase: there is no project concept outside Backlog's `project_key` (`scripts/testign/config.py:41-43`), so nothing existing fills the gap. `Bridge._agent_view` passes only `params` of the job (`scripts/testign/console/jobs.py:905-907`), so the `webtest-run` job cannot carry the project unless the run does.
- **Suggested fix:** Store `project` in `run.json` (`webtest-new --project`) and derive the run's allowed hosts from the project's hosts plus run-only extras, in one place. Drop the job-level `hosts` parameter.

## Finding 7: The `login` ask is answered by the server from a child process, which bypasses the anti-self-approval rule
- **Severity:** High
- **Location:** Phase 4, section "Login prompts"; Phase 5, section "Starting a login" steps 2-3; Phase 7, Login scenarios screen "Sign in"
- **Flaw:** The plan adds a seventh ask type, `login`, and a new server path that answers it when the runner child ends. Today every answer goes through `Bridge.answer`, which refuses browser sessions opened after the job started. That rule exists so that "a session minted by the agent during the job cannot approve its own questions". The plan does not say that `POST /api/webtest/login/:project/:scenario/run` applies the same age check. The Login screen also has its own "Sign in" button with no job, so sign-in has two entry points with different semantics.
- **Failure scenario:** During a run job, page text injected into a row tells the agent to open a fresh console tab (a new browser session) and POST `/run`. The runner signs in, and the server sets `{signed_in: true}` on the open `login` ask with no `answered_by` and no age check. The queue continues under a scenario the tester never approved for this job. Separately, a tester presses "Sign in" on the Login screen before the job asks. No ask exists to answer, so the session is live but `webtest-next --signed-in` is never told. Acceptance 6 ("has been run in this session") is then decided by whichever path ran last.
- **Evidence:** `scripts/testign/console/jobs.py:662-668` (session-age rule and its stated reason); `jobs.py:675-681` (the only code path that sets `ask["answer"]`, with `answered_by`); `jobs.py:218` (closed list of ask types); `jobs.py:123-152` (a `questions` ask with two options already gives "Signed in" / "Skip scenario").
- **Suggested fix:** Use a `questions` ask (Signed in / Skip this scenario) for both routes. The runner's success only shows on the Login screen, and the tester confirms through the normal answer path. If the server-set answer is kept, the `/run` route must apply the same session-age check against the open job, and must record `answered_by` from the starting session.

## Finding 8: The review table is a new ask type and a new view built in parallel with the existing review screen
- **Severity:** Medium
- **Location:** Phase 4, "Review-table ask (blocking)"; Phase 7, "Screens" (Review table) and "Files to Create / Modify"
- **Flaw:** Dense asks already have a route: `jobs.mjs` renders only `questions` inline and sends the `REVIEW_TYPES` set to `#/jobs/<id>/review`, rendered by `review.mjs`. Phase 7 puts `review-table` into `ask-form.mjs` and a new `review-table.mjs`. It does not touch `jobs.mjs`, `review.mjs` or `main.mjs`. The rule "a delegated `choice` row needs preconditions" is checked three times: in the UI (phase 7 test), in server `validate_answer` (phase 4) and in `webtest-plan` (phase 2). The server check also requires the server to read the scenario store and understand triage semantics.
- **Failure scenario:** A `review-table` ask arrives. `jobs.mjs` neither renders it inline (not `questions`) nor links it to the review screen (not in `REVIEW_TYPES`). The Jobs screen shows a `needs-input` job with nothing to click, and the tester is stuck at the one confirmation the plan depends on. Later, a rule change (for example, `visual` moving to `choice` as phase 8 foresees) has to be made in three languages of code.
- **Evidence:** `scripts/testign/console/ui/views/jobs.mjs:16` (`REVIEW_TYPES = ['review-rows','confirm-diff','paste-pages']`); `jobs.mjs:220` (inline only for `questions`); `scripts/testign/console/ui/views/review.mjs:13,87-93` (review screen dispatch by type); `scripts/testign/console/ui/main.mjs:22` (`VIEWS` map); `scripts/testign/console/ui/router.mjs:44-47` (`#/jobs/<id>/review`); `scripts/testign/console/jobs.py:153-180,248-271` (`review-rows` already carries per-row edits).
- **Suggested fix:** Add `review-table` to `REVIEW_TYPES` in `jobs.mjs` and `review.mjs` and render it on the existing review route. Keep the triage rule in `webtest-plan` (the CLI owns run semantics). The server checks shape and sizes only, as it does for `review-rows`.

## Finding 9: Interface changes on kinds and the job record miss consumers that break, while the planned server work is mostly a no-op

Add `job-actions.mjs` (`requeueBody`, `jobTitle`), `main.mjs`, `FAIL_REASONS` and the `job_reason_not_confirmed*` keys to Phases 4 and 7, and state that `test_console_jobs.py:123` is updated on purpose.

## Finding 10: Console-only scenario authoring and Chrome launching go beyond "the agent offers to create one"
- **Severity:** Medium
- **Location:** Phase 5, "Creating a scenario" first bullet and "Commands" (`chrome-profile --open`, `login-project-set`); Phase 7, Login scenarios screen ("New, edit steps", "add a sign-in host")
- **Flaw:** The request is: a menu of scenarios per project, the tester chooses, and the agent offers to create one when missing. The plan adds a second, agent-free creation path: a console form where the tester writes `goto/fill/click/wait/manual/expect` steps with CSS selectors by hand. It also adds a step editor, a per-project sign-in host editor and a CLI that starts a dedicated Chrome. Each is a separate write path into `~/.testign-kit/webtest/` that needs its own server validation (closed step kinds, host checks) on top of `login-scenario-save`. This is the main reason Phase 7 is the largest phase (4 days).
- **Failure scenario:** The console form and `login-scenario-save` validate the same `scenario.json` through two code paths, one in the server and one in the CLI. A rule fix (for example, refusing `fill` on a field not in `fields`) lands in one of them, and a hand-written scenario that the CLI would refuse runs through the fixed runner. The templates screen already shows this cost: it re-implements role mapping in the UI (`templates.mjs:305-355`) beside the CLI's `--map`.
- **Evidence:** `scripts/testign/console/ui/views/templates.mjs:11-12,305-313,355` (UI copy of registry rules: `ROLES`, `REQUIRED`); `scripts/testign/templates.py:20-21,249-253` (the CLI's copy of the same rules); `scripts/testign/console/templates_api.py:172-200` (server re-validates the UI's input).
- **Question (requested-scope doubt, not a cut):** Does the tester need to write scenarios by hand, or is "agent drafts, tester reviews and edits selectors in a draft view, tester approves" enough? If the hand path stays, both the console and the CLI should call one validator in `login_scenarios.py`. The plan should state that the server imports it rather than re-implementing it.
