## Finding 1: A row left `running` permanently blocks the run; "Queue again" is refused
- **Severity:** Critical
- **Location:** Phase 2, section "Commands" (`webtest-next`, `webtest-close`); Phase 3, section "Export" step 1; Phase 4, sections "Kinds" (`webtest-run`) and "Parked row questions" (last bullet)
- **Flaw:** Every command that could move the run forward refuses a run with a `running` row, and no command or route moves a `running` row anywhere except `webtest-row` and `webtest-park`, which belong to the dead job's orchestrator. The server never touches `run.json`, so job failure does not reset row state. The two stores drift by design, and nothing reconciles them.
- **Failure scenario:** Row r17 is handed to the worker (`webtest-next` marked it `running`). Any of these then happens: the terminal is closed, the session hits context limits, the tester presses "Release agent", another session takes over after 15 min of silence, `console stop --force` runs, the server restarts, or the orchestrator calls `console wait` by mistake (which fails the job `not-closed`). The job ends as `failed`. The tester presses "Queue again". The `webtest-run` kind check refuses the run ("has no `running` row"). The tester cannot queue a job, run `webtest-next`, close the run or export. The only way out is to hand-edit `run.json`, which phase 2 treats only as something to detect and refuse. Acceptance 3 ("No row is left `queued` or `running`") and the "continue a stopped run" path in phase 6 both fail on the most common crash.
- **Evidence:** Plan phase 4: "`webtest-run` | `run` an existing run id whose plan is confirmed and which has no `running` row"; phase 2: `webtest-next` refuses "A run that already has a `running` row", `webtest-close` refuses "A run with a `running` row"; phase 4: "'Queue again' starts a new `webtest-run` job on the same run, which continues from `run.json`". Job failure paths that leave `run.json` untouched: `jobs.py:460-470` (startup → `server-stopped`), `jobs.py:773-778` (`wait` → `not-closed`), `jobs.py:695-707` (takeover → `session-lost`), `jobs.py:637-654` (release), `jobs.py:628-635` (mark failed), `lifecycle.py:349` (`stop --force`). No `webtest-*` route or hook in the bridge.
- **Suggested fix:** Store the owning job id in `run.json` when a row becomes `running` (`webtest-next --job <id>`). Allow `webtest-run` to queue when the owning job is no longer open. Make the first step of a run job `webtest-recover --run <id> --job <new>`: a `running` row whose owner is finished goes back to `queued` with an `interrupted` note, and its stray evidence is kept but unlinked. Add a test: restart the server mid-row, then queue again, and the run completes.

## Finding 2: Parks and self-run results live only in the dead job; a continued run silently turns them into `not-run: unanswered`
- **Severity:** High
- **Location:** Phase 4, section "Parked row questions"; Phase 6, section "Skill: run job" steps 3 and 5
- **Flaw:** A parked row has state in `run.json` (`parked`), but its question, the tester's answer and any self-run result live in the job record (`parks`), keyed to one job id. A new job starts with an empty `parks`. The `done` guard and `console parks --wait` count only that job's parks. Also, `webtest-park` (run.json) and `console park` (job record) are two separate, non-atomic writes.
- **Failure scenario:** (a) Job J1 parks r05 and r09. The tester answers r05 with "delegate". Then the server restarts before the orchestrator polls. J1 fails. J2 is queued on the same run. J2's `parks` is empty, so `console parks` returns `open: 0`. When the queue is empty, the orchestrator calls `webtest-close`. r05 and r09 become `not-run: unanswered` even though the tester answered r05 and was never asked again about r09. (b) The orchestrator runs `webtest-park` and the session dies before `console park`. The row is `parked` in `run.json`, the tester sees no question, and the `done` guard does not block. (c) J1 is pruned after 7 days or 50 finished jobs, so the answers the plan says are kept "for the Jobs screen" are deleted.
- **Evidence:** Plan phase 4: "Stored in the job record as `parks`, keyed by row"; "A failed or cancelled job leaves its parks in the record for the Jobs screen"; "`Bridge.done` with `done` is refused while a park is unanswered". The record is per job (`jobs.py:590-609`, no run link). Startup keeps the record but fails the job (`jobs.py:460-470`). Prune: `jobs.py:51-52`, `474-485`.
- **Suggested fix:** Make `run.json` the source of truth for open questions. On start, a run job re-issues `console park` for every `parked` row (idempotent per park id). Carry over answered-but-unapplied parks from the newest earlier job on the same run (the job summary already gains `run`). Do `webtest-park` and `console park` in a fixed order, and have the re-issue step repair a missing half.

## Finding 3: Park answers keyed only by row, with no park id, re-apply stale answers and make `webtest-resolve` fail on redelivery
- **Severity:** High
- **Location:** Phase 4, section "Parked row questions" (`console parks`, "each answer is handed out until acknowledged"); Phase 2, `webtest-resolve`; Phase 6, "Skill: run job" step 5
- **Flaw:** Redelivery until ack is at-least-once delivery, but `webtest-resolve` is not idempotent ("Refuses: an answer that does not fit the row's state"), and parks have no question id or generation. The existing ask channel protects against this with unique ask ids (`console-bridge.md:33-35`). Parks do not.
- **Failure scenario:** (a) The orchestrator gets r05 → `delegate`, runs `webtest-resolve` (r05 goes back to `queued`), and is killed before `parks-ack`. On the next poll r05 → `delegate` is handed out again. The row is now `queued`, or `running` if `next` already picked it, so `webtest-resolve` exits 2 and the skill's "never retry the same failing call" rule (`skills/console/SKILL.md:103`) leaves the answer unacknowledged forever. `open` never reaches 0, and the end-of-queue `parks --wait` waits until the tester presses Finish. (b) r05 is delegated, re-runs, and parks again with a new question. The unacknowledged first answer is keyed by the same row, so it resolves the second park without the tester seeing the new question. (c) If the skill acks before resolving, a crash in between loses the answer, and the row closes as `not-run: unanswered`.
- **Evidence:** Plan phase 4: "`{answers: [{row, answer}], open: <n>, finish: true | false}`; each answer is handed out until acknowledged"; "`console parks-ack <job> --session <s> --row <r>`". Phase 2 `webtest-resolve` refusal. Existing id-based protection: `jobs.py:838-845` ("this ask id was closed without an answer; use a new id").
- **Suggested fix:** Give each park a `park_id` (row plus attempt number) and store the applied `park_id` in `run.json`. Make `webtest-resolve --park-id` a no-op that succeeds when that id is already applied, and ack by `park_id`. Refuse a second `console park` for a row while an earlier park for it is unacknowledged.

## Finding 4: The `login` ask and the fixed runner are loosely coupled: success is dropped, scenarios cross, and a hung or orphaned runner has no stop path
- **Severity:** High
- **Location:** Phase 5, sections "Starting a login" (steps 2 to 5) and "Commands" (`login-run`); Phase 4, section "Login prompts"
- **Flaw:** The server answers "the open `login` ask" when any runner succeeds. It does not check that an ask is open, that the ask names the same scenario, or that the job is still the same job. On the runner route the only other answer is `skip_scenario` ("Signed in" exists only on the manual route). The plan has a 409 for a second start but no stop or kill route, and no rule that kills the child on server exit.
- **Failure scenario:** (a) The tester signs in proactively from the Login screen before the orchestrator reaches the scenario. No ask is open, so the success is dropped (`answer` needs `needs-input`). When the orchestrator then asks, the tester presses "Sign in" again. The site redirects the signed-in user away from `/login`, the `fill #email` step fails, and "a runner that ends with a failed `expect` leaves the `login` ask open". The run is stuck with no "Signed in" button. (b) The job asks for `member`. The tester runs `admin` from the Login screen, it succeeds, and the server answers the `member` ask with `signed_in: true`. The orchestrator calls `webtest-next --signed-in member`, and member rows (including delegated data rows) run as admin. (c) On route D1, Chrome shows an approval dialog for each connection (research:48). The tester is away, so the runner blocks on the WebSocket, and every retry gets 409 until the runner timeout. (d) The server is stopped (`console stop` falls back to SIGTERM, which skips the shutdown hooks) or restarts. On Windows a child does not die with its parent. The runner keeps typing into Chrome, the new server's in-memory "one runner" flag is clear, and a second runner starts on the same login tab.
- **Evidence:** Plan phase 5: "On success the server answers the open `login` ask with `{signed_in: true}`"; "One runner at a time; a second start while one runs gets 409"; phase 4: "on the manual route the tester presses 'Signed in'". Code: `jobs.py:669-671` (answer only while `needs-input` with an open ask); `lifecycle.py:363` (SIGTERM fallback); `lifecycle.py:434-441` and `server.py:581-583` (hooks only on graceful exit); `lifecycle.py:192-197` (detached process groups, so nothing kills children with the parent).
- **Suggested fix:** Bind a runner start to `{job, ask_id, scenario}` and answer only that ask. Record a runner success per scenario with a timestamp, so a later `login` ask for the same scenario is answered at once. Offer "Signed in" on the runner route too. Add `POST .../run/stop`. Kill the child from a shutdown hook. Write the runner PID to `~/.testign-kit/webtest/runner.json` and kill a stale runner on server start. On Windows, put the child in a job object or kill it with `taskkill /T`. Give every DevTools socket read a timeout.

## Finding 5: Environment failures (site session expiry, extension disconnect, JS dialog) are recorded as per-row `stuck`, which cascades into mass parking and permanent reclassification
- **Severity:** High
- **Location:** Phase 6, sections "Worker brief" (the `stuck` list) and "Skill: run job"; Phase 2, section "Row states" ("A `sure` row that parks moves to class `choice`")
- **Flaw:** The worker contract has one outcome for every non-row problem. A login page is the normal sign of an expired site session, and it is listed as `stuck`. A park permanently flips `sure` to `choice`, and requeueing a `choice` row needs tester-written `preconditions`. Nothing detects "the environment broke" and pauses the queue to re-open the `login` ask.
- **Failure scenario:** The test site's session expires after 30 minutes, about 20 rows into the run. Every remaining `member` row shows the login page. Each one is handed to a worker, costs a full worker turn, ends `stuck`, is parked and is reclassified `choice`. The tester comes back to 25 park questions. Re-running them needs 25 `delegate` answers, each with preconditions text, and the report lists 25 "class changed during the run" rows that were never ambiguous. The same cascade follows when the Claude in Chrome service worker goes idle (research:29, "Browser extension is not connected") or when a JS `alert` blocks the shared tab group (research:27): every later tool call fails.
- **Evidence:** Plan phase 6: "A login page, a CAPTCHA, a browser dialog, a host outside the list, a missing element after the steps ... ends the row as `stuck`"; phase 2: "A `sure` row that parks moves to class `choice`"; phase 4: "`delegate` (needs `preconditions`)". Research: `research/researcher-01-chrome-figma-facts.md:26-29`. The existing asks have no auto-retry, so the only channel left is the per-row park (`jobs.py:832-868`).
- **Suggested fix:** Add a worker outcome `blocked-env` with a cause (`login`, `extension`, `dialog`) and a CLI transition `running → queued` that does not reclassify the row. After the first `blocked-env: login`, the orchestrator drops the current `--signed-in` and re-opens the `login` ask. Stop the queue after N consecutive `blocked-env` results. Flip the class only for row-specific `stuck`.

## Finding 6: The Figma import has no place to save partial progress, crosses the 15-minute silence window, and can exceed the daily cap on retry
- **Severity:** High
- **Location:** Phase 6, section "Skill: plan job" step 2; plan.md, "Load-bearing assumptions" row 5; Phase 1, section "Risks" (second bullet)
- **Flaw:** "Save each row as it arrives ... resume later from the saved rows. Then `webtest-new` and `webtest-import`" puts the saving before the run folder exists. No command stores a partial import. `webtest-import` refuses a second import, so partial rows cannot be appended. `webtest-find` only finds runs that already hold an import. Pacing 135 to 180 calls at 10 per minute runs past the bridge's 15-minute silence limit unless the skill sends progress lines.
- **Failure scenario:** 45 rows × 3 calls (research:85), plus about one ancestor call per row for screen guesses (phase 1 risks), gives about 180 calls. On a Professional Full seat that is 18 minutes at 10 per minute, against a 200-per-day cap. At minute 15 with no console call, the job is "silent". The tester can mark it failed, and another session can take it over. Or a rate-limit error stops the import at row 30. Either way the job ends, the saved rows exist only in the conversation or a temp file, and the next plan job's `webtest-find` finds nothing and starts from row 1. The second attempt needs another ~180 calls, which runs past the daily cap of 200. Acceptance 1 ("a second import of the same node makes no Figma call") holds only for a completed import.
- **Evidence:** Plan phase 6 step 2: "save each row as it arrives, and on a rate-limit error stop and resume later from the saved rows. Then `webtest-new` and `webtest-import`"; phase 2: `webtest-import` refuses "A second import"; `webtest-find` "Lists runs that already hold an import". Code: `jobs.py:48` (`SILENT_WITH_JOB = 15 * 60`), `jobs.py:523-528`, `jobs.py:632` (mark failed after silence), `jobs.py:695-707` (takeover). Research: `researcher-01-chrome-figma-facts.md:78`, `:85`.
- **Suggested fix:** Run `webtest-new` first. Add `webtest-import-stage --run <id> --row <file>`, which appends one row to `source/partial.jsonl`, and have `webtest-find` report partial imports with their row count. Then `webtest-import` finalises from the staged rows. Require `console progress` at least every few minutes during paced imports. Record the calls used in `run.json` so a resume knows its remaining budget.

## Finding 7: The review-table answer is dropped from the job record before `run.json` holds it, and `webtest-plan` cannot be checked against what the tester confirmed
- **Severity:** Medium
- **Location:** Phase 4, sections "Review-table ask (blocking)" and "Risks" (first bullet); Phase 2, `webtest-plan`
- **Flaw:** The plan drops the review table "from the record once answered; only the confirmed plan (in `run.json`) is kept". `run.json` gets the plan only when the agent later runs `webtest-plan --plan <agent-written file>`. Between those two steps, the only copy of the tester's 45-row edits is in the agent's process. The existing bridge re-hands a lost answer because the answer stays in `asked`, so dropping it removes that recovery. Also, `webtest-plan` takes an agent-written file and does not fetch the confirmed answer from the console. `wiki-update` does fetch it (`cli.py:385-399`), so the two stores can disagree without anyone noticing.
- **Failure scenario:** The tester spends 20 minutes editing screens, scenarios and preconditions for 45 rows and confirms. The `console ask` command was cut off by the 2-minute Bash limit (`console-bridge.md:26-31`), or the session dies before `webtest-plan`. If the answer was dropped, re-asking the same id cannot return it, and the tester redoes the table. Separately, a compacted or confused orchestrator writes a plan that differs from the answer, for example `runner: agent` on a `choice` row the tester left unset. The CLI accepts it, because preconditions text is present and nothing compares the plan with the console.
- **Evidence:** Plan phase 4 risks: "The review table is dropped from the record once answered; only the confirmed plan (in `run.json`) is kept." Code: `jobs.py:838-842` (re-hand-out of an answered id), `jobs.py:855-858` (answer stored in `asked`), `console-bridge.md:33-35`, `cli.py:385-399` (`wiki-update --job --session` fetches the confirmed approval from the console).
- **Suggested fix:** Drop the large ask payload, but keep the answer (or its hash) in `asked` until `webtest-plan` succeeds. Have `webtest-plan --job <id> --session <s>` fetch the confirmed answer from the server and refuse a plan file that differs from it, following the `wiki-update` pattern.

## Finding 8: "Finish" cannot stop the queue or a pending login, and a run job stuck in held calls can only be killed by "Release agent"
- **Severity:** Medium
- **Location:** Phase 4, section "Parked row questions" (`finish`) and "Login prompts"; Phase 6, section "Skill: run job"; Phase 2, "Row states" (`not-run: ... stopped`)
- **Flaw:** The loop reads `finish` only in the end-of-queue `parks --wait`. Step 5 inside the loop says only "apply each answer". During a `login` ask the orchestrator is held in `console ask`, which returns only an answer or `null`, so it never sees `finish`. Also, `done(done)` is refused while the job is `needs-input`. "Mark failed" is refused while any held call is open, because silence counts as 0. The `stopped` reason in the state diagram is produced by no command, and phase 4 says open rows become `unanswered`. The two texts disagree.
- **Failure scenario:** The tester needs to leave and presses "Finish with open rows" at row 10 of 45. The orchestrator keeps running the other 35 rows (possibly hours of Chrome driving, and delegated data rows). Or the job is waiting on a `login` ask whose runner keeps failing. Finish does nothing, "Mark failed" returns 409 because the held call keeps silence at 0, and the only exit is "Release agent". That fails the job as `session-lost`, and then Findings 1 and 2 apply.
- **Evidence:** Plan phase 4: "`POST /api/jobs/:id/finish` sets `finish: true` ... The orchestrator then closes the run; open rows become `not-run: unanswered`"; phase 6: "When the queue is empty and parks are open, call `console parks --wait` until every park is answered or the tester presses 'Finish'". Code: `jobs.py:526-527` (silence 0 while held), `jobs.py:632` (mark failed refused), `jobs.py:851-868` (ask returns only answer or null), `jobs.py:884-886` (done refused while `needs-input`), `jobs.py:637-654` (release).
- **Suggested fix:** Have the server end any open `login` ask with `{finish: true}` when Finish is pressed. Return `finish` from `console progress` and check it after every row. Define the order (current row ends, then `webtest-close --reason stopped` for `queued` rows and `unanswered` for `parked` rows). Let "Mark failed" work on a run job that is waiting on a held call.

## Finding 9: Self-run results have no durable home: the route is job-scoped, uploads are swept after one hour, and nothing waits for them
- **Severity:** Medium
- **Location:** Phase 4, section "Parked row questions" (self-run result bullet); Phase 2, "Row states" (`runner tester ─▶ self-run`); Phase 3, "Export" step 1; plan.md acceptance 3
- **Flaw:** Self-run results go to `POST /api/jobs/:id/rows/:row/result`, so a job must be open to take them. The evidence goes into the shared upload folder, which the server deletes after one hour and at every start. The existing upload route also accepts only xlsx (`check_zip`), so the PNG/JPEG route is new and not the "existing" one. Rows set to `runner: tester` at confirmation are not parks, so neither the `done` guard nor `parks --wait` waits for their results. Export refuses only `queued`, `running` and `parked` rows, so a `self-run` row with no result exports as if it were final.
- **Failure scenario:** At confirmation the tester marks 6 rows `runner: tester`. The agent runs the other 39 rows, the queue empties with no open parks, and the job closes and exports. The 6 rows appear as `self-run` with empty results, which breaks acceptance 3 ("`self-run` (with the tester's result)"). The tester opens the Run screen to enter them, but no job is open to accept them. Or the tester uploads an image during a run, the session dies, and the continuation job starts 90 minutes later. `webtest-evidence --from-upload` gets "no such upload (it may have expired)".
- **Evidence:** Plan phase 4: "the orchestrator copies it into the run folder with `webtest-evidence --from-upload`"; phase 3: export refuses "a `queued`, `running` or `parked` row". Code: `templates_api.py:29` (`UPLOAD_TTL = 3600`), `templates_api.py:87-101` (sweep), `templates_api.py:207-219` (sweep at install and hourly), `templates_api.py:128-130` (`check_zip` on every upload), `templates_api.py:106-113` (expired upload → 404).
- **Suggested fix:** Add a row state `awaiting-tester` for `runner: tester` rows that counts as open for `done`, close and export, or have the orchestrator park them as `self-run` questions. Let the server copy the uploaded image into a run-scoped staging folder under `~/.testign-kit/webtest/` at upload time, not after the next poll. Accept self-run results through a run-scoped route that works without an open job, and apply them in the next run job.

- **Location:** Phase 2, section "Commands" (`webtest-row` evidence refusal) and "Run folder" (`evidence/<row>-<n>.png`); Phase 6, "Skill: run job" step 3; Phase 1, item B route 2 with item D1

It does not tie the file to the current attempt or the current `running` interval. `webtest-evidence` and `webtest-row` are two non-atomic steps. On route D1, every DevTools connection shows an approval dialog (research:48), and phase 1 says item D decides item B's second route.
- **Failure scenario:** (a) r12 parks because a login page appeared, and `r12-1.png` (showing the login page) is saved before the park. The tester delegates it, the row re-runs, and the worker returns `pass` with `evidence_ready: true`, but capture fails silently. (b) `webtest-evidence` writes `r12-2.png` and the session dies before `webtest-row`. Finding 1 then strands the row, and the orphaned file is later reused as in (a). (c) On D1, each of 45 captures pops a Chrome dialog. An unattended run blocks at the first capture, with no timeout on `webtest-evidence`. When the worker opened a new tab (behaviour rows), capture may also pick the wrong CDP target in the shared tab group.
- **Evidence:** Plan phase 2: "`pass` or `fail` without an evidence file that exists in `evidence/`"; "`evidence/ <row>-<n>.png, written by the evidence command`"; phase 1: "Item D decides item B's second route: both need a debug connection. D1 is preferred". Research: `researcher-01-chrome-figma-facts.md:48` (dialog per connection), `:27-28` (dialogs block; one shared tab group). The existing never-overwrite naming pattern (`xlsx.py:26-32`) keeps old attempt files beside new ones.
- **Suggested fix:** Have `webtest-evidence` record `{name, attempt, captured_at}` in `run.json` against the current `running` attempt, and have `webtest-row` accept only names captured in that attempt. Add a capture timeout and a target chosen by the worker's final URL or tab id. If D1 is chosen, hold one DevTools connection for the whole run so the tester approves it once, not once per row.
